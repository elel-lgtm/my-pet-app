# Supabase

Local Supabase CLI workspace. `config.toml` was generated by `supabase init` (CLI 2.115.0) and is
the CLI's own default template — it contains no credentials.

> The schema exists and is locked down. Because RLS is enabled and no policy has been written,

> `auth.uid()` means anything would have to be either wrong or dangerously permissive.

## Prerequisites

The CLI is **not** a project dependency — it is a large platform binary CI has no use for. Run it
through `npx`, pinned:

```bash
npx supabase@2.115.0 --version
```

Pinning means a CLI upgrade is a deliberate commit rather than a surprise on someone's machine.

The **local stack** (`supabase start`) additionally needs Docker Desktop. Docker is not installed on
the current development machine, so that workflow is documented from the CLI's interface but has
**not been executed here**. Everything below that touches the remote project has been run.

## Credentials

`login` and `link` involve credentials and are run by the project owner on their own machine:

```bash
npx supabase@2.115.0 login
npx supabase@2.115.0 link --project-ref <project-ref>
```

`link` prompts for the **database password**. It is privileged, is not needed by the app, does not
belong in `.env`, and must never be committed. The CLI stores it outside the repository.

`<project-ref>` is the subdomain of the project URL and is not a secret. The `service_role` /
`sb_secret_…` key **must never enter this repository or the app bundle** — it bypasses row-level
security entirely.

## Everyday commands

npm scripts wrap the common ones:

```bash
npm run db:push:dry     # show what would be applied
npm run db:push         # apply pending migrations
npm run db:types        # regenerate lib/supabase/database.types.ts
npm run db:verify       # run the constraint suite (rolled back; changes nothing)
npm run db:advisors     # Supabase's security and performance lint
```

Underneath they are `supabase db push --linked`, `supabase gen types typescript --linked`, and so
on. With Docker available, `supabase start` / `db reset` / `stop` give a throwaway local stack whose
printed URL and key go in `.env.local`, never in `.env.example`.

## Migration workflow

```bash
npx supabase@2.115.0 migration new <name>   # always the CLI, never a hand-placed file
# edit the generated SQL
npm run db:push:dry                          # inspect what will run
npm run db:push                              # apply
npm run db:verify                            # prove the constraints bite
npm run db:types                             # regenerate types, then commit them
```

The migration list and the two rules governing them (RLS enabled in the creating migration;
forward-only, never edited after pushing) are in [migrations/README.md](migrations/README.md).

Before applying anything to a real project, the sequence used in this phase is worth repeating: run
the concatenated migrations inside `begin; … rollback;` via `supabase db query`. That proves the SQL
executes cleanly against the actual server version and leaves nothing behind, which a `--dry-run`
does not — it only lists which files would run.

## Generated types

`lib/supabase/database.types.ts` is produced by `supabase gen types typescript --linked` and
describes the live schema. `AppSupabaseClient` is `SupabaseClient<Database>`, so every query is
checked against real columns and enum values at compile time.

**Regenerate it in the same change that alters the schema, and commit it.** A stale type is worse
than none: it type-checks against a database that no longer exists.

It is excluded from Prettier and ESLint — it is regenerated wholesale, never hand-edited. ESLint
also blocks `app/`, `components/`, and `features/` from importing it: `Database` describes rows, not
the domain, and only data adapters translate between the two.

`lib/supabase/__tests__/database-types.test.ts` asserts every domain union against its database enum
at compile time, so a drift between the two fails CI rather than production.

## Testing the schema

`tests/constraints.sql` attempts writes that must fail and writes that must succeed, inside a
transaction that is rolled back. 39 checks; every row of the output must read `ok`.

```bash
npm run db:verify
```

It is not a Jest test on purpose: it needs a real PostgreSQL instance, and the Jest suite must never
depend on a live project. It found one genuine bug in this phase — see the `cardinality` note in
[../DATABASE.md](../DATABASE.md).

## What must never be in this directory

The database password · the `service_role` / `sb_secret_…` key · the JWT secret or signing keys ·
`.env`, `.env.local`, or any file with real credentials.

`supabase/.gitignore` (generated by the CLI) excludes `.temp`, `.branches`, `.env.local`, and
`.env.keys`. The repository root additionally ignores `.env` and `.env.*` everywhere.
